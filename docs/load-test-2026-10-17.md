# בדיקת עומס: 50,000 אוהדים (17.10.2026)

## עדכון: אחרי התיקונים (17.10.2026, ענף `perf-fixes`)

**מה תיקנו.** כל ארבעת תיקוני בסיס הנתונים נכנסו כמיגרציה אמיתית עם בדיקות (שמראות שכל אוהד רואה בדיוק אותו
דבר כמו לפני התיקון), והאפליקציה עצמה תוקנה בשני מקומות:
- כשקריאה נכשלת, המסך אומר "לא הצלחנו לטעון. נסה שוב" עם כפתור, במקום להראות אפס או רשימה ריקה. זה בפעמון,
  ברשימת ההתראות, בצ'אט הקבוצה, בחדר המשחק, בתיבת ההודעות, בכיכר ובחלקים של דף הבית. בנוסף: אוהד שהפרופיל שלו
  לא נטען כבר לא נשלח בטעות למסך ההרשמה.
- השגיאה שהשרת רשם בכל טעינת דף (כ-1,500 פעם בכל ריצה) נעלמה לגמרי: 0 בשתי הריצות האחרונות.

**מה מדדנו.** הרצנו שוב את אותה בדיקה בדיוק (50,000 אוהדים, אותו מחשב, אותו עומס) שלוש פעמים על הקוד המתוקן.

|---|---|---|
| בקשות שנכשלו | 15%-25% | 8.5%-13% |
| בקשות שנכנסו | 178-218 אלף | 203-234 אלף |

**מה זה אומר.** שתי השאילתות שתקעו את כל השאר כבר לא תוקעות. הכשלונות שנשארו (כ-9%) הם תור בשרת הביניים של
בסיס הנתונים, כשכל הבדיקה רצה על מחשב אחד עם 4 מעבדים; בשרתים האמיתיים זה שונה, וזה לא משהו בקוד שלנו. וכשבקשה
כן נכשלת, האוהד רואה "לא הצלחנו לטעון" ולא מידע שגוי. דוגמה מהריצה: בזמן העומס צ'אט הקבוצה לא הצליח לטעון, והמסך
אמר את זה במקום להיפתח כמעט ריק.

**מה נשאר.** לאשר ולמזג את הענף, להעלות את המיגרציה קודם לסביבת הבדיקות ואחר כך לאתר. ובחירת תוכנית Supabase לפי
כמות החיבורים בזמן אמת (משימה 6) עדיין פתוחה.

## בקצרה, בשביל יאיר (הבדיקה הראשונה, לפני התיקונים)

**מה עשינו.** בנינו "אצטדיון מזויף" בתוך מחשב בדיקה של GitHub: עותק מקומי וריק של כל השרתים שלנו, ומילאנו
אותו ב-50,000 אוהדים מזויפים עם היסטוריה (מיליון הודעות בצ'אט הקבוצות, 225 אלף בחדרי משחק, 9,000 פוסטים בכיכר
עם 400 אלף לייקים, חצי מיליון הודעות פרטיות מוצפנות, דירוגים, ניחושים ומלחמת קהלים). כל הנתונים מסומנים
"נתוני עומס". האתר האמיתי, בסיס הנתונים האמיתי ו-Vercel לא נגעו בכלום.

אחר כך הפעלנו את האפליקציה האמיתית (אותו קוד שבאוויר) ו"שחררנו" עליה בבת אחת 2,000 אוהדים שגולשים
(בית, צ'אט, חדר משחק, כיכר, הודעות פרטיות, דירוגים, פעמון), 2,000 טלפונים שמחוברים בזמן אמת, 60 אוהדים
שטוענים דפים מלאים, ובאמצע "גול": 300 הודעות בשנייה בחדר המשחק. בזמן העומס ואחריו רובוט פתח את האפליקציה
במסך של טלפון ובדק שמה שרואים על המסך זהה למה שיש בבסיס הנתונים.

**מה החזיק.**
- אחרי העומס, כל הבדיקות עברו: הצ'אט מראה בדיוק את ההודעות האחרונות לפי הסדר בלי חורים, הודעה של אוהד אחד
  מופיעה אצל אוהד אחר תוך פחות משנייה, ספירת הלייקים, מלחמת הקהלים, הפעמון ותיבת ההודעות זהים לבסיס הנתונים.
- אף דף לא נהיה רחב מהמסך (אין "באג פריסה"), גם תחת עומס.
- המונים שהבסיס סופר לבד (לייקים, נקודות במלחמת הקהלים, מספר אוהדים) נשארו מדויקים אחרי מאות אלפי פעולות.
- 2,000 חיבורי זמן אמת נפתחו בבת אחת והחזיקו ברובם הגדול עד הסוף (לפי הריצה, בין 6 ל-252 התנתקו באמצע והתחברו מחדש).

**מה נשבר.**
1. **שתי שאילתות "כבדות" תקעו את כל השאר.** ספירת הטרמפים למשחק הבא (בדף הבית) ורשימת הביקורות על השחקנים
   (גם בדף הבית) לקחו יחד כ-78% מזמן העבודה של בסיס הנתונים. בגלל זה כל הבקשות האחרות עמדו בתור, 15%-25% מהן נכשלו
   אחרי 10 שניות המתנה, והדפים נטענו לאט מאוד.
2. **כשבקשה נכשלת, האפליקציה מראה מידע שגוי במקום להגיד "לא הצלחנו".** תחת עומס ראינו פעמון בלי מספר כשהיו
   5 התראות, תיבת הודעות עם שיחה אחת במקום חמש, וצ'אט קבוצה שנפתח עם 2 הודעות במקום 50.
3. **בזמן "גול" ההודעות בחדר המשחק עמדו אחת אחרי השנייה** בגלל מנעול אחד לכל משחק בתכונת "דעת הקהל".
4. **בתוכנית החינמית של Supabase זמן-אמת מוגבל ל-200 טלפונים ול-100 הודעות בשנייה.** בבדיקה עם המגבלות
   האלה כ-83% מההודעות בזמן אמת פשוט לא הגיעו. ל-50,000 אוהדים חייבים תוכנית בתשלום מתאימה.

**מה לתקן קודם** (התיקונים כבר כתובים ונבדקו על אותם נתונים. לא שינינו כלום באפליקציה עצמה. עדכון: 1-4 בנויים
בענף `perf-fixes`, ראו למעלה):
1. שתי השאילתות הכבדות (טרמפים וביקורות): פי 11 עד פי 36 מהר יותר, אותה תוצאה בדיוק. בבדיקה חוזרת עם התיקון
   הכשלונות ירדו מ-15%-25% (בלי התיקון, בשתי ריצות) ל-8.5% (עם התיקון, בשתי ריצות), ונכנסו 8%-33% יותר בקשות.
2. אינדקס חסר אחד בדירוגים ("הדירוגים שלי"): מ-5 מילישניות ל-0.2.
3. המנעול של "דעת הקהל" בזמן גול.
4. האפליקציה צריכה להגיד "לא הצלחנו לטעון" ולנסות שוב, במקום להראות אפס.
5. לפני ההשקה: לבחור תוכנית Supabase שמתאימה לכמות החיבורים בזמן אמת (משימה 6 במרכז החברה).

**חשוב להבין.** כל הבדיקה רצה על מחשב אחד עם 4 מעבדים, שהריץ באותו זמן את בסיס הנתונים, את השרתים, את
האפליקציה, את 4,000 ה"אוהדים" ואת הרובוט. זה הרבה יותר חלש מהשרתים האמיתיים. לכן מספרי הזמן המוחלטים (כמה
שניות לקח) גרועים יותר מהאמת. מה שכן אמין: **איזה חלק נשבר ראשון ולמה**, וכמה התיקון עוזר כשמשווים אותו
מחשב, אותה כמות ואותו עומס, לפני ואחרי.

## How it was run

Workflow `.github/workflows/web-load-local.yml` on one `ubuntu-latest` runner (4 vCPU, 15 GB RAM). It never
touches the hosted Supabase projects or Vercel: no GitHub environment, no secrets, and every script refuses a
non-local URL (`127.0.0.1`, `localhost` or a private Docker address).

1. `supabase start` (CLI 2.120.0, same pin as `web-db.yml`) applies every migration to a fresh local stack.
2. `apps/web/load/seed.sql` seeds 50,000 auth users + profiles and their history set-based in about 60 s (triggers off
   while seeding, every trigger-kept counter computed at the end; everything labelled "נתוני עומס"; private messages are
   random ciphertext-shaped strings; media rows only, Storage object rows without files).
3. `next build` + `next start` of the real app against the local stack (`NEXT_PUBLIC_APP_ENV=local`).
4. `apps/web/load/mint-tokens.mjs` signs sessions for 5,000 sampled fans with the local stack's JWT secret: the access
   token for k6, and the same session as the `@supabase/ssr` cookie so Server Components render as that fan.
5. `apps/web/load/explain.sql`: EXPLAIN ANALYZE of the hot queries as a seeded fan under RLS, plus "what-if" blocks
   that apply a proposed fix inside a transaction, measure it on the same data and roll it back.
6. k6 (`apps/web/load/fans.js`), all at once: `api` (2,000 VUs, the same PostgREST / RPC / Storage calls as
   `src/features/**`), `goal` (300 match-room messages/s for 50 s in the live match, 30% with the crowd keyword
   "פנדל"), `pages` (60 VUs loading the real pages with the fan's cookie), `realtime` (2,000 websockets joining
   `online:<club>` with presence, `team:<club>`, `inbox:<me>`, and `match:<id>` + `room:<id>` for the two live clubs).
   Ramp 120 s, hold 300 s, goal window 60 s, ramp down 30 s.
7. Playwright (`apps/web/load/consistency.spec.ts`, 375 px, reserved seeded fans 1-20 that k6 never acts as) during
   the hold and again after the load.
8. `apps/web/load/report.sh` + `report.sql`: job summary from k6, `pg_stat_statements` (reset just before k6),
   table sizes, sequential scans, a recount of trigger-kept counters, container CPU (sampled every ~10 s), container
   logs. The same report is re-emitted as check-run annotations (`annotate.sh`), because artifacts are not reachable
   from the Claude sandbox.

Rerun: push a change to `apps/web/load/run.env` on the `load-test` or `perf-fixes` branch, or (once the workflow is on
`main`) `gh workflow run web-load-local.yml -f users=50000 -f vus=2000 -f ws=2000 -f page_vus=60 -f goal_rate=300 -f hold=300`.
Since migration `20261017090000_perf_fixes` the fixes are part of every run; `fixes=1` (re-apply `load/proposed-fixes.sql`)
is kept only for the record of the experiment.

### Two local-stack settings changed for the test (and why)
- **Realtime tenant quotas** were raised through Realtime's management API (local defaults: 200 concurrent users,
  100 events/s, 100 joins/s, which are the Free plan's published limits) so that the runner, not a quota, stops
  the test. Run 38977827778 kept the defaults on purpose (see finding 5).
- **k6 talks straight to the PostgREST, Storage and Realtime containers** (private Docker addresses on the runner).
  The CLI's local Kong runs one nginx worker; with 2,000 keep-alive connections plus websockets it stopped answering
  (run 38980272878: 99.2% of requests failed with EOF, Kong logged DNS-resolution timeouts for its upstreams,
  Realtime never got past 245 sockets). Hosted Supabase runs its own, scaled gateway, so this is a test-machine limit.
  The Next.js app and the Playwright browser still go through Kong (few connections).

## Findings: our code and database

### 1. Trip count on the home page: two security functions per trip row (biggest cost)
- **Evidence.** Baseline: `HEAD trips?fixture_id=eq.…` (the home's "טרמפים למשחק" count, `stand-home/server/queries.ts`)
  = 3,766 calls, **1,002 s of database time, 266 ms mean, 2,081 ms max**: the largest single cost of the run
  (with finding 2, 78% of the database time of the top 25 statements). EXPLAIN on the seeded data: 22.8 ms for one
  count.
- **Root cause.** The restrictive select policies `trips_not_ride_suspended` and `trips_verified_or_hidden` call
  `private.ride_suspended(user_id)` and `private.ride_poster_ok(user_id, kind)` (security definer, not inlinable) for
  **every row**. The count reads every trip of the match, so the cost is trips × fans opening the home.
- **Fix** (`load/proposed-fixes.sql` §1; same rows, checked: 338 = 338): read the active suspensions once per query
  and short-circuit the verification check while the switch is off.
  ```sql
  create function private.active_ride_suspensions() returns uuid[] language sql stable security definer set search_path = ''
    as $$ select coalesce(array_agg(s.user_id), '{}') from public.ride_suspensions s where s.lifted_at is null $$;
  create function private.ride_verification_on() returns boolean language sql stable security definer set search_path = ''
    as $$ select private.setting_on('rides_require_verification') $$;
  -- grant execute on both to authenticated
  alter policy trips_not_ride_suspended on public.trips using (
    (user_id = (select auth.uid())) or (select public.is_app_admin())
    or user_id <> all (coalesce((select private.active_ride_suspensions()), '{}')));
  alter policy trips_verified_or_hidden on public.trips using (
    (user_id = (select auth.uid())) or (select public.is_app_admin())
    or not (select private.ride_verification_on())
    or private.ride_poster_ok(user_id, kind) or private.accepted_on(id));
  ```
- **Measured.** EXPLAIN 22.8 → 0.63 ms. Under load: 266 / 125 ms mean (baselines A / B) → 7.2 / 7.1 ms (fixes runs).
- Once ride verification is switched on, `ride_poster_ok` runs per row again: before switching it on, replace it with
  a once-per-query set as well (verified poster ids), and add a pgTAP test that the policy still hides unverified posts.

### 2. `home_player_reviews()`: `blocked_between()` per candidate review
- **Evidence.** Baseline: 4,008 calls, **783 s, 195 ms mean**. EXPLAIN: 17.7 ms per call.
- **Root cause.** `not public.blocked_between((select auth.uid()), x.user_id)` runs for every review the lateral scan
  looks at (definer function, plan per call).
- **Fix** (§2; same answer, checked with a checksum of the rows): one definer helper returns the fans blocked either
  way, read once per call:
  ```sql
  create function private.blocked_ids(p_me uuid) returns uuid[] language sql stable security definer set search_path = '' as $$
    select coalesce(array_agg(x), '{}') from (select b.blocked_id x from public.blocks b where b.user_id = p_me
                                              union select b.user_id from public.blocks b where b.blocked_id = p_me) z $$;
  -- in home_player_reviews, instead of: and not public.blocked_between((select auth.uid()), x.user_id)
  and x.user_id <> all (coalesce((select private.blocked_ids((select auth.uid()))), '{}'))
  ```
- **Measured.** EXPLAIN 17.7 → 1.6 ms. Under load: 195 / 103 ms mean (baselines) → 14.3 ms (both fixes runs).
- Next step if the home grows: the club part (top reviews per player) is the same for the whole club and can be
  cached per club like `home_active_fans`; only `liked` and the blocked filter are per fan.

### 3. Missing index: `player_ratings (user_id)`
- **Evidence.** `player_ratings?select=player_id,stars,review&user_id=eq.<me>` (`getSquadWithRatings`, every stand /
  ratings view): 54 ms mean in the baseline, 31 ms with fixes 1-2. EXPLAIN 5.1 ms: an index scan of the whole primary
  key `(player_id, user_id)` because `user_id` is its second column.
- **Fix:** `create index player_ratings_user_idx on public.player_ratings (user_id);` (also used by account deletion).
- **Measured.** EXPLAIN 5.1 → 0.19 ms; the statement left the top 25 in 38985418523.

### 4. Crowd verdict during a goal: one lock per match serialises the room's writes
- **Evidence.** Match-room insert: 60 ms mean, 592 ms max in the baseline (team-chat insert 41 ms at the same time);
  goal-burst requests p50 10.1 s.
- **Root cause.** `match_messages_crowd`: once 15 fans wrote a crowd keyword in 60 s, **every** further keyword
  message calls `crowd_tick()`, which takes `pg_advisory_xact_lock(hashtext('crowd:' || fixture))` and holds it until
  that insert commits. The poll is already open, so the work is useless, but every writer of the room waits for the
  previous one.
- **Fix** (§4): in the trigger, `if c >= 15 and pg_try_advisory_xact_lock(hashtext('crowd:' || new.fixture_id)) then
  …` — a message that finds the lock taken skips the tick; the next message or the app's own `crowd_tick` call does it.
  Checked locally: 16 fans shouting "פנדל" still open exactly one poll.
- **Shipped** in migration `20261017090000_perf_fixes` (through `private.crowd_try_lock`, so the pgTAP test can simulate a
  busy lock). Trade-off, tested in `perf_fixes.test.sql`: a keyword message that finds the lock busy is still counted in
  the burst (15 distinct fans counted while the lock was busy) but does not open the poll itself; the next keyword
  message of the burst opens it, exactly once. If the very last message of a burst is the one that met the busy lock,
  the poll waits for another keyword message (`crowd_tick` alone does not open chat polls). The other three fixes ship
  in the same migration; `home_player_reviews` uses `private.my_blocked_ids()`, which takes no fan id (the experiment's
  `blocked_ids(uuid)` could have told who blocked whom between two other fans).
- **Measured.** Match-room insert mean 60 / 41 ms (baselines) → 39 ms (fixes 1-2) → **29 ms** (fixes 1-4); goal-burst
  p50 10.1 / 10.0 s → 7.8 → 6.9 s; goal messages written 1,663 / 2,148 → 1,850 → 2,366 in the same 50 s.
- Also worth doing: skip the burst bookkeeping entirely when a poll of that kind opened in the last 3 minutes.

### 5. Realtime quotas (plan limits) drop most live messages
- **Evidence.** Same 5,000-fan load twice: with the local defaults (200 concurrent users, 100 events/s — the Free
  plan's published limits) k6 received **21,545** broadcasts (run 38977827778) and Realtime logged 3,330
  `UnableToBroadcastChanges: too_many_requests` and 17 `ConnectionRateLimitReached: Too many connected users`; with
  the quotas raised it received **128,912** (run 38979052952). About 83% of the live messages never arrived, and the
  UI check "message appears in another fan's open chat" failed 3 of 3 during that load.
- Supabase's published Realtime limits ([Realtime limits](https://supabase.com/docs/guides/realtime/limits)): Free
  200 concurrent connections / 100 messages/s / 20 presence messages/s; Pro 500 / 500 / 50; Pro without spend cap and
  Team 10,000 / 2,500 / 1,000.
- **Presence.** Every page tracks the fan in `online:<club>` (`OnlineTracker`), so each join or leave fans out to every
  other fan of the club: 241,853-299,868 presence events reached the 2,000 test sockets in 520 s, and Realtime logged
  `PresenceRateLimitReached` (the presence quota was not raised for the test). At 50k fans this is the first realtime limit to hit.
  Proposal: count "online now" without presence fan-out (e.g. a periodic server-side count broadcast per club), or
  track presence only on the screens that show the count.
- **Action:** choose the Supabase plan by realtime connections and messages per second (task 6 in `docs/COMPANY.md`).

### 6. A failed read shows wrong data instead of "could not load"
- **Evidence.** During the peak the bell showed no count while the database had 5 unread (`getUnreadCount()` returns 0
  on error), the inbox showed 1 chat instead of 5 (`getInbox` keeps going when one of its queries fails), and the team
  chat opened with 2 messages instead of the last 50 (`getTeamMessages()` returns `[]` on error, then realtime adds
  the new ones). All pages answered 200.
- **Fix:** return an error state from these queries and show "לא הצלחנו לטעון · נסה שוב" (or keep the last known value)
  instead of 0 / an empty list; same review for every `data ?? []` fallback in `features/*/server/queries.ts`.
- **Done (branch `perf-fixes`).** The query helpers behind the bell (`getUnreadCount`), the activity list, the team chat,
  the match room, the inbox (`getInbox`: null when any of its three reads fails), the Square (feed, likes, respects and
  signed URLs) and the home sections and tiles (stories, players, hot posts, chat preview, fans of the week, the four
  counts) return null on a failed read, blocked-fans read included (`getBlockedIdsOrNull`). The screens show
  `components/load-error.tsx` ("לא הצלחנו לטעון. נסה שוב", the button refreshes the screen) instead of the empty state;
  "load more" keeps its button and says it failed instead of ending the list. The bell shows "!" with the label
  "התראות, לא הצלחנו לטעון. נסה שוב", reads again every 10 s while unknown, and a later failed read keeps the last known
  count. The two cached club numbers throw inside `'use cache'`, so a failure is not cached. Found by after 2: a failed
  profile read made `getSessionProfile` say "no profile" and the layout redirected the fan to onboarding; it is now
  `status: 'error'` with the same message and no redirect. Unit tests for every error path (`*/server/queries.test.ts`).
  Not changed: the crowd polls of the match room and the "my ratings" squad on the home still fall back to empty on a
  failed read (no counts shown wrongly, but the same review applies), and the private thread screens load their history
  in the browser and show an empty thread if that read fails.

### 7. Next.js logs an error on every page render: the browser Supabase client is created while rendering on the server
- **Evidence.** `next start` logged `Route "/…": Next.js encountered the unstable value Date.now() while prerendering`
  1,498 times in the baseline (1,490 with the fixes) (every route of the signed-in app); stack:
  `__loadSession → _useSession → _emitInitialSession` (auth-js).
- **Root cause.** `useState(() => createClient())` in `features/activity/components/bell.tsx` and
  `features/push/components/alert-banner.tsx` (both in the app layout, so on every page; also `inbox-list.tsx`,
  `dm-thread.tsx`, `group-thread.tsx`) runs during server rendering; the client's auth initialisation reads the clock.
- **Fix:** create the browser client lazily in the browser only (in the effect that uses it, or
  `lib/supabase/client.ts` returning a module singleton created on first use in the browser). Pages still render; the
  cost is an error object + stack per request and noisy logs that hide real errors.
- **Done, and the root cause above was only part of it (branch `perf-fixes`).** Moving the browser client into effects
  (bell, alert banner, inbox list, private and group threads, `useDeviceKey`; `lib/supabase/client.ts` keeps one client
  per tab) did not change the count: after 1 still logged ~1,490. The stack is the auth-js session load that every
  Supabase client runs when it is created, and the server client (`lib/supabase/server.ts`) loads the session from the
  cookie and checks its expiry right away. It now awaits `connection()` (Next.js's own advice in the error) before it is
  created, so it is never made inside a prerender. After 2 and after 3: **0** such errors (`report.sh` now counts them).
  Tests: `bell.server.test.tsx` renders the bell and the banner on the server without creating the browser client;
  `lib/supabase/server.test.ts` checks the order cookies → connection → client.

### Checked and fine
Indexes and keyset pagination hold at this size: team chat page 0.6 ms, match room page 0.2 ms, Square first page and
keyset page 5 ~0.09 ms, my likes of a page 0.07 ms, inbox 0.06 ms, a thread page 0.1 ms, bell unread 0.3 ms, crowd-war
totals 0.02 ms (EXPLAIN on 50k). Sequential scans during the load were on small tables where the planner is right to
scan (`market_items`, `fan_events`, `players`, ≤ 1,000 rows); the few sequential scans of big tables
(`team_messages`, `clip_likes`, `dm_messages`) are the seed and the report's own counts (the counters are cumulative
since the stack started; under 10 scans each). Trigger-kept counters were exact after the load (likes, crowd-war totals, team fan counts:
0 mismatches). No deadlocks.

Trigger cost per write (EXPLAIN, 50k): team-chat insert 1.7 ms warm (moderation 0.8 ms of it; the first insert on a
new connection pays ~5-9 ms to compile the moderation patterns), match-room insert 2.9 ms, Square like 3.3 ms (the
activity notification 1.9 ms of it), private message 1.6 ms.

## Test-machine limits (not our code)

- **One 4-vCPU runner ran everything.** Load average 25-28 at peak; k6 alone used ~2.8 cores; PostgREST, a single
  process, ~1 core; Postgres 1.3-2.1 cores. After fixes 1-4 Postgres was no longer saturated (130%); the remaining 8.5%
  failures were PostgREST pool timeouts with PostgREST and k6 competing for the same CPUs.
- **PostgREST pool = 10 connections** (local default, `PGRST_DB_POOL` unset). p95 ≈ 10.2 s in every 50k run is exactly
  the pool's acquisition timeout. Hosted Supabase sizes this pool by compute; check it on the plan chosen.
- **Realtime delivery times at 50k are not trustworthy.** k6 parsed 1.2-1.5 million broadcasts on a starved CPU;
  send → received p50 was about 3.1 s (team) and 18-50 s (match), while Realtime's own CPU stayed at ~50%. At 5,000
  fans on the same machine k6 measured 6-7 ms p50 (25-52 ms p95), and at 50k the browser check right after the load
  saw 7-40 ms.
- **Page times include the shared CPU and the PostgREST queue.** Pages p50 12-13 s at 50k vs 87-141 ms at 5k.
- **The local Kong** (one nginx worker) failed first when k6 went through it (run 38980272878); hosted Supabase does
  not use it.
- **Sign-in tokens are minted locally (HS256)**: with a symmetric key `getClaims()` validates them by calling the
  Auth server on every render (here: the local one, 20% of a core at peak). Not measured separately; with asymmetric
  signing keys the check is local.
